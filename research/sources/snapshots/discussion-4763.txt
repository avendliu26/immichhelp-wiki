jrasm91

Maintainer
Libraries don't currently use checksums since they are the "source of truth" and there is a significantly negative performance impact to generating hashes on large libraries. Even if we had them, checksums have to be unique in the database and now you still have the complexity of managing what file do you keep and which one do you ignore, how do you manage that on rescan or file moves, etc. There are also priorities for libraries like automatic album creation. I guess long story short, probably not going to be addressed anytime soon and you are better off using a proper dedupe tool instead.

jrasm91
Oct 24, 2023
Maintainer
External libraries are quite different than upload libraries and we have separate implementations, which reflect each use case.
Upload libraries have immich as the source of truth and it manages creating and deleting files and deduping them.
External libraries have the file system as the source of truth and so we leave creating, deleting and deduping files to the user. Deduping has different semantics in this context and the implementation would be quite different. We realized that by not having hashing it is
significantly
faster to import an external library, so we didn't add it.
It is not to say hashing and other deduping
cannot
be done, it is more that it is not trivial as it seems and specifically because there were benefits to excluding it (simpler implementation) we didn't include it originally.
Checksum is a required field, but the value for external library files is just a hash of the file path instead.

jrasm91
Oct 25, 2023
Maintainer
Pre-existing duplicates I agree are a separate problem with no easy answer. It was just a surprise that backing my photos up through a separate mechanism (which is indeed recommended upfront in the documentation) results in duplicate uploads from the mobile app to my library.
Honestly, there seem to be two main types of users using Immich right now:
I want immich to backup and organize my photos for me.
I have my own collection of photos I'll give you read only access to them, don't touch them.
Immich was originally designed to work exactly like google photos. With google photos you don't have an option 2 available in the first place. But, there are lots of people looking for self-hosted photos with use case 2 in mind, so libraries was
added
(after the fact) to accommodate that user group. Upload libraries are really for group one and external libraries are really for group two.
While we
want
to support more use cases, photo management software is indeed complicated. I'd say, currently at least, using the upload library and the external libraries in tandem in not a great experience and I think most people are only using one or the other right now. I'm sure it will improve in the future, but it is a current limitation. It's still unclear exactly how they should/will be integrated in the future. There are talks of migrating "partner sharing" to be library based and other stuff like that.
I would be really interested to learn more about how the current implementation works to check duplicates against images in the upload_location but the code base is massive and I didn't have any luck trying to search on my own. Any pointers on where to look?
Hashes are calculated on upload
here
Hashes are have a unique database constraint (per library)
here
Asset uploads are passed to the service
here
. If the upload violates the constraint the error is caught and the duplicate id is returned.
Library checksum fields are set
here
Side note: why not use md5 rather than sha1 since it's a bit less computationally expensive? (EDIT: I guess the speed is fairly comparable, but you get more bits from sha1...)
Long story short, it is the version Alex picked when he started building, probably because he is not a crypto expert and just made a decision and moved on. By the time more contributors started working on the project sha1 was already widely incorporated into the project and it would take a bit of effort to migrate to another algorithm. The benefits of migrating simply was not worth the time and effort. Basically, migrating has minimal impact on the users of the system, but delays other more critical features that we've decided to build instead. So like, do you want to migrate to md5 or get a better search system, a stacked photos implementation, a more robust dedupe implementation, automatic albums for external libraries, etc. We've decided those features are more important than the algorithm we use for hashing. Sha1 is pretty performant still and on some machines is a single cpu instruction.

hodlemperor
Nov 14, 2025
Hi, I just had my issue "Missing cross-source deduplication between External Libraries and Upload Library" (
#23898
) closed in favor of this one, so I’d like to add some context and clarify my use case here.
I’ve read through this discussion and I understand the current design and intentions:
Upload libraries = Immich is the source of truth, with real checksums and dedup.
External libraries = the filesystem is the source of truth, no real checksums, no dedup, and the user is responsible for managing duplicates inside that library.
I’m not asking Immich to modify or deduplicate files
inside
the external library itself. I fully agree that the external library should stay read-only and that “in-library” dedupe is the user’s job.
My problem is specifically about how
assets from different sources are represented in the timeline and in mobile backup workflows
, not about touching the external filesystem.
1. This
could
be mitigated by merge duplicates, but only in theory
In some cases, the situation could be partially mitigated by using the
Merge duplicates
feature:
the device uploads a photo that already exists in an external library
Immich detects a duplicate
the user merges and chooses which asset to keep
However, even this has several issues:
it
wastes bandwidth and server resources
, because the duplicate must be fully uploaded
before
it can be merged
it is
manual
, so it doesn’t scale for large overlapping libraries
and most importantly: it
still doesn’t work
correctly unless the other issue is solved:
Mobile backup re-uploads deleted duplicates after 30 days because Immich does not remember excluded hashes (
#23897
)
If I keep the External Library asset and delete the Upload Library asset, after Trash expires the mobile app will upload the same file again.
So even with the merge feature, the loop continues unless the server can remember that this hash was intentionally excluded as an upload.
2. Realistic migration workflows: people keep old photos on their phone
From a user perspective, it is also important to highlight that this is not an edge case:
Many people have
years or decades
of photos on their phone (e.g. old imports, device migrations, etc.).
It is completely normal to still have photos from 2006 or earlier on the phone, even if they also exist in some archive.
When migrating to Immich, it is not realistic to expect users to:
delete all existing photos from their phone and only keep them in an external library,
or
“sanitize” their external library so that it never overlaps with whatever still lives on the device.
On top of that, a lot of users (myself included) have
previous backup systems that they no longer fully trust
.
A very common migration pattern is:
keep the old backup on the NAS (external library)
keep photos on the phone as well
use Immich to:
verify that everything is really there
detect if something is missing
and only then decide how to clean up
In this scenario,
overlapping content between the phone and an external library is not a mistake, it’s intentional and temporary
, and Immich is used as the tool to reconcile and verify.
3. Two distinct but related issues
For me there are two separate layers:
Mobile backup + deleted uploads
As described in
Mobile backup re-uploads deleted duplicates after 30 days because Immich does not remember excluded hashes
#23897
: if I merge and keep the External Library asset while deleting the upload, after 30 days the mobile client will re-upload the same photo, creating an infinite loop.
This is about the server not remembering hashes that the user explicitly excluded.
Cross-source duplication in the UI
Even without the re-upload loop, when the same file exists as:
an uploaded asset, and
an External Library asset
they appear as two separate photos in the timeline, even if the content is identical.
I understand that full hashing for external libraries is expensive and was intentionally avoided to keep them fast and simple. I’m fine with this being treated as a feature request rather than a bug.
However, I think it’s important to acknowledge that:
using
External Libraries + mobile backup together
is a very realistic use case,
people will almost always have
overlapping content
between their phone and their external collections,
and today, the combination of:
no cross-source deduplication, and
no memory of excluded upload hashes
makes this workflow quite painful (duplicates, loops, extra bandwidth use, manual merges).
4. Possible direction (from a user perspective)
Without changing the external filesystem, some ideas that would already help a lot:
Optional hashing for external libraries (opt-in, with clear warnings about performance).
Timeline-level deduplication/stacking when two assets share the same real content hash.
Remember hashes that were explicitly deleted from the upload library (so mobile backup doesn’t re-upload them).
Better UX around merge, deletion, and “don’t ever upload this file again”.
Thanks again for all the work and for the detailed explanations above. I hope this additional perspective (especially about real-world migration workflows and the interaction with mobile backup) is useful when you revisit libraries and cross-source behavior in the future.
For reference, the related issue about excluded hashes is
#23897
.
