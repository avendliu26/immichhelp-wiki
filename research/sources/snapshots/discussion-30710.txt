Adding details from my own instance, which looks like it might narrow this down — I'm hitting the exact same "Error Loading Image" symptom, but my logs actually contain a specific error message (mine says logs show nothing, some other reports in this thread say the same, so maybe this varies by asset type).

Immich version:
v3.1.0

)

Library: ~20k assets, mostly phone-shot JPEGs/HEIC and some video —
no RAW camera files
in the affected set as far as I can tell

After upgrading to v3.1.0, thumbnails broke across a large chunk of the library (not just newly synced items — existing assets that displayed fine before the upgrade).
Full stack restart (
docker compose down
/
up -d

Administration → Jobs → Thumbnail Generation →
Missing
— no change.
Administration → Jobs → Thumbnail Generation →
All
— same assets fail every time.

Every failure in my server log is the same handler error:

Given

MediaService.decodeImage
is routing ordinary JPEG/HEIC assets through the RAW decode path and failing there — rather than a corrupt-file or storage-path issue.
Key finding: it's deterministic, not flaky

Exactly 183 assets fail both times, and it's the same 183 asset IDs both times
(verified by diffing the failing asset IDs from each log). This isn't random/transient — the same specific assets consistently hit this code path and fail, while the rest of the library thumbnails fine. That suggests something about those particular files (format variant, embedded metadata, color profile, etc.) is triggering the RAW-loader branch in
decodeImage
, rather than a systemic library-wide problem.

Same here. I'm seeing the same issue on v3.1.0 (native install via community-script on Proxmox LXC, not Docker) and traced it a bit further, which might help narrow down the cause.
Setup: immich-web and immich-ml both run as systemd services under the
immich
user (confirmed via
systemctl show
and
ps
). No Docker involved.
What I found:
Affected assets DO have a matching row in
asset_file
for both
preview
and
thumbnail
types, with a valid-looking path.
The files at those paths physically exist on disk and are non-corrupt (normal file sizes, e.g. 24-28KB webp).
However, several of these thumbnail files are owned by
root:root
with permissions
600
(rw-------), even though every immich process on the system runs as user
immich
.
A newly generated thumbnail (created after re-running the "Missing" job) was correctly owned by
immich:immich
, also with
600
permissions.
Since the serving process runs as
immich
and cannot read files owned by
root
with mode 600, the API request for that thumbnail fails - this shows up as a 404 in the browser console rather than a 403, which is what pointed me toward permissions rather than a missing/corrupt file.
Re-running "Generate Thumbnails > Missing" did NOT pick up these already-broken assets, since the DB already has an
asset_file
record for them - the job doesn't consider them "missing."
Manually running
chown -R immich:immich
on the thumbs directory fixed the already-broken ones, but doesn't address the root cause of some job writing files as
root
in the first place.
Given that this is a non-Docker/native systemd setup and I still see
root
-owned files despite every process running as
immich
, it doesn't look like a Docker-user-mapping issue (as sometimes cited for similar reports) - the root ownership is happening within the app itself for some subset of thumbnail-generation runs. Worth checking if there's a job path (e.g. one triggered indirectly, such as during a metadata-extraction pass) that briefly executes with different privileges or a different working context than the standard thumbnail worker.
Happy to pull more logs/DB output if useful.
