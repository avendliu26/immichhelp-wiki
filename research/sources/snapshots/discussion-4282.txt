I’m adding my specific case here since my issue (
#23897
) was closed as a duplicate — and after reading this thread, I fully agree that it belongs here.
There is one important scenario that makes this problem even more severe:
✔ When using an External Library (+ mobile backup enabled)
If a photo exists both:
on the phone (mobile backup), and
in a read-only External Library
Immich cannot remember that the user
intentionally
deleted the upload version after a merge.
Once Trash expires, the mobile app sees the file as “missing” and re-uploads it again → creating a duplicate again → and the cycle repeats forever.
✔ Merge duplicates does
not
fix this in practice
Technically, the user can merge duplicates:
keep the External Library asset
delete the upload version
…but after 30 days, the deleted-upload is gone, Immich forgets the hash, and the phone uploads the same file again.
So even the merge workflow is broken unless Immich can permanently remember excluded hashes.
✔ Realistic migration workflows make this unavoidable
This is also not an edge case.
Most users have:
years or decades of photos remaining on their phone (even from 2006 or older),
previous backup systems they don’t fully trust,
overlapping content between phone and NAS/External Library while checking that everything was backed up correctly.
It is not realistic to expect users to:
wipe their phone before migrating, or
sanitize their entire External Library so that it never overlaps with their mobile library.
✔ The feature requested here (a permanent “deleted hash registry”) is exactly what solves it
A server-side list of hashes that were intentionally deleted would:
prevent mobile clients from re-uploading them
make the merge workflow actually viable
stop duplicate loops
allow External Libraries + mobile backup to coexist without chaos
Thanks — this FR is absolutely essential for users combining mobile backup with External Libraries.

verisgit
Apr 27, 2026
Found a bit of a clunky workaround for the time being; it's tedious, but better than 30k photos and videos resurrecting themselves on every backup run.
Immich iOS — Stop Deleted/Deduplicated Photos Re-syncing
Problem
The iOS client has no awareness of server-side deletions. Every sync cycle it re-uploads anything it thinks is missing — including photos you've already deleted or deduped within immich, constantly repopulating anything you've cleaned up on the server.
Solution
Use a manually managed excluded iOS album as a sync fence.
Steps
1. Let Immich fully sync your library first.
Don't delete or deduplicate anything yet. Upload all photos from your phone.
2. Create an album in iOS Photos called
excluded
.
3. Select your entire library and add it to the album.
iOS has no "select all" — workaround: scroll to the end of your library, tap
Select
, drag back to highlight a few photos, then with your other hand tap the
clock icon
to jump to the top. Everything in between gets selected. Add to
excluded
.
4. In Immich → Backup Settings, add
excluded
to the excluded albums list.
Previously synced photos won't re-upload. New photos aren't in the album yet, so they'll sync normally.
Ongoing
After every sync to Immich, you will need to figure out what new photos were added and then manually add them to
excluded
. This prevents them from being re-uploaded if you later edit or delete it server-side.

alextran1502
Jul 17, 2026
Maintainer
Anything with destructive nature should be explicit and taken with care and with human supervision. So that is why we are not wanting to hide it via a "hash registry" solution to silently not updating things again and will cause so much confusion to the users why some assets are not uploading, the counts are then mismatching.
The solution we are going for is very explicit.
You delete assets on the web
When you open the mobile app, it sees that you are deleting these assets and they are still presented on your local device, it would ask you if you also want to delete these assets on your local device.
The goal is to have a pristine and explicit communication about the deletion process.
The complexity is how to propagate to all the data flow path that the app has, and how to make it work with all use cases.
Those are my simple answers to the problem we are trying to solve. If you want to read more about the LLM counter arguments of why it is not so simple, feel free to read more below.
Click to expand!
Why "just add a deleted-hash registry" is 10% of the feature
The registry table itself is trivial — nobody disputes that. Every hard part of this feature lives in the questions that sentence doesn't answer, and they're the same questions
#28280
is grappling with.
"Deleted" is not one event. Assets go through trash → permanent deletion, and permanent deletion happens from at least five code paths: explicit "delete forever," trash emptying, the trash retention job, library offline-file cleanup, and account deletion — plus utilities like the duplicate-dedupe flow that delete assets as a side effect of keeping another copy. Which of these record intent-to-never-see-again? If the duplicate utility tombstones the hash of the copy it discarded, and that byte-identical file exists on your second phone, backup silently skips it forever. If external-library cleanup tombstones, re-adding a file to a watched folder stops working. Each path needs an explicit decision, and each wrong default is a data-loss bug report. The registry also has to be written at trash-empty time, not delete time, and unwound on restore — across all of those paths, atomically with bulk jobs.
The failure mode is silent data loss in a backup product. Hash-matching is a guess about intent. The moment the guess is wrong — user deleted accidentally, trash auto-emptied after 30 days, and they still have the photo on their phone believing it's backed up — the system silently refuses to back it up, indefinitely. "But there's force upload" only helps if the user knows something was skipped. So now you need: a rejected-uploads surface on mobile and web, per-asset review, badges/counts, and a way to clear registry entries. That is precisely the "approve deletions" UX in
feat(mobile): review remote-trashed assets before syncing deletions
#28280
that this thread is calling over-engineered. The complexity wasn't invented by the maintainers; it's inherent, and it reappears the moment you make the simple version safe.
It's an API-contract change with a client fleet in the wild. Upload dedupe today is a two-state contract: created or duplicate (asset-media.service.ts returns AssetMediaStatus.DUPLICATE with the existing id, and mobile marks the local asset backed up; /assets/bulk-upload-check works the same way in batch). A tombstone introduces a third state: "rejected, and no asset exists." Every client — both mobile platforms, the CLI, third-party tools built on the SDKs — must handle it and persist it locally, or their backup loop re-hashes and re-attempts those files on every single pass forever. Old clients that don't understand the new status will treat it as an error and surface perpetual backup failures. So: OpenAPI change, both SDKs, mobile local-state schema, CLI, and a version-skew story for servers ahead of clients.
It has to participate in multi-device sync anyway. The proposal quietly assumes one phone. With two devices (or a reinstalled app), the "don't re-upload this" state must reach every client — otherwise device B re-attempts everything device A's deletions tombstoned, hitting point 3's retry problem at scale. That means tombstones become a synced entity type in the v2 sync stream (which already has to model AssetDeleteV1, partner deletes, album-asset deletes as distinct events, with checkpointing and acks), with all the ordering and backfill questions that entails. "The server just rejects it" doesn't remove the state from the system; it moves it somewhere clients rediscover it the expensive way.
Hashes are a weaker identity than this thread assumes. The checksum is over file bytes, and the ecosystem loves rewriting bytes: iOS transcoding/re-export, iCloud offload-and-redownload, Google Takeout metadata stripping, edits, even re-saving. The registry fails open on every one of those — the photo comes back anyway — so the feature is unreliable in many of the exact scenarios that generate this complaint, while adding permanent risk in the scenarios where it does match. And as a bonus, "Immich keeps hashes of things I deleted, forever" is itself a retention/privacy surface that needs a management UI and a growth policy.
The maintainers' direction attacks the root cause; the registry hard-codes one guess. The actual defect is that backup is one-way: deletion intent never propagates to the device, so device and server disagree forever.
feat(mobile): review remote-trashed assets before syncing deletions
#28280
makes the deletion an explicit, user-resolvable sync event — which subsumes this request (choose "keep deleted, don't re-upload" and you get your registry behavior) and handles the accidental-deletion case without silent loss. The registry, by contrast, bakes in one answer ("server deletion always wins, silently") and still needs most of the same plumbing (new API state, client persistence, multi-device propagation, review UX) once you patch its failure modes.
So: the disagreement isn't about whether a hash table is easy to create. It's that "compare against a registry and skip" is a one-line description of a cross-cutting change to the upload contract, the sync protocol, five deletion paths, three client platforms, and the failure semantics of a system whose one job is not losing people's photos. "Simple" versions of sync-adjacent features are how you end up with the bug reports that take years to live down.

Prevent re-uploading intentionally deleted assets
Another important requirement is that Immich should remember assets that were already uploaded and then intentionally deleted from the server.
Currently, when a photo still exists on the phone and is deleted from the Immich server, the mobile backup may upload the same photo again. This creates an unwanted loop:
The photo is uploaded from the phone.
The photo is intentionally deleted in Immich.
The mobile app detects that the photo is missing from the server.
The same photo is uploaded again.
Immich should provide two separate deletion options:
Delete and prevent this asset from being uploaded again
Delete but allow the asset to be uploaded again later
The server could store the checksum of intentionally deleted assets in an exclusion list. The mobile app should then recognize that the asset was already processed and deliberately deleted.
This is especially important for family accounts, duplicate cleanup and workflows that combine mobile uploads with an external photo library.
